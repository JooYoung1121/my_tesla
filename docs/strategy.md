# 마이 테슬라 전략 문서

최종 업데이트: 2026-06-10

## 기본 원칙

이 프로젝트의 문서, 화면 문구, 메뉴명, 버튼명, 카테고리명은 모두 한글을 기본으로 한다. 기술 고유명사인 TeslaMate, Vercel, Supabase, PostgreSQL, Grafana, MQTT 같은 이름은 원문을 유지한다.

## 목표

8월쯤 테슬라 모델 Y를 인수하기 전후로 필요한 정보를 한곳에 모으는 개인용 웹앱을 만든다.

이 앱은 테슬라 공식 앱을 대체하지 않는다. 공식 앱은 차량 제어와 기본 관리를 맡고, 이 프로젝트는 다음 역할을 맡는다.

- 인수 전 준비 체크리스트
- 테슬라 카페와 공개 커뮤니티 정보 정리
- 썬팅, PPF, 블랙박스, 충전기, 보험, 액세서리 의사결정
- 인수 당일과 첫 한 달 해야 할 일
- 충전 비용, 주행 기록, 관리 기록
- 추후 TeslaMate 같은 차량 데이터 로깅 도구와 연결

## 현재 판단

지금 바로 TeslaMate를 직접 구현하거나 대체 앱을 만들 필요는 없다. 먼저 개인 정보 허브와 커뮤니티 정보 큐레이션 앱을 만든다.

TeslaMate는 차를 실제로 인수한 뒤, 장기 주행/충전/배터리 데이터를 쌓고 싶을 때 별도 서비스로 붙이는 편이 맞다.

## 추천 기술 조합

1순위는 Vercel 기반이다.

- 웹앱: Next.js
- 배포: Vercel
- UI: Tailwind CSS, 필요한 경우 shadcn/ui 일부 사용
- 차트: Recharts 또는 Tremor
- 데이터베이스: Supabase PostgreSQL 또는 Neon PostgreSQL
- ORM: Prisma 또는 Drizzle
- 이미지 저장: 지금은 불필요, 추후 필요하면 Cloudinary
- 인증: 처음엔 개인용 단순 비밀번호, 이후 NextAuth/Auth.js 검토

개인용이라도 Vercel 프로덕션에서는 로컬 파일 DB를 믿고 쓰기 어렵다. Vercel 함수 실행 환경은 영구 디스크처럼 쓰는 구조가 아니므로, 배포 버전에서 저장이 필요하면 외부 DB를 두는 것이 안전하다.

로컬 DB는 다음 용도로만 쓴다.

- 개발 중 테스트
- 오프라인 개인 실험
- 백업용 SQLite 파일
- 실제 서비스 전 임시 저장소

## 데이터베이스 선택

### Supabase PostgreSQL

가장 추천한다.

장점:

- 개인 프로젝트에 충분히 편하다.
- PostgreSQL이라 확장성이 좋다.
- 관리자 화면에서 데이터를 직접 보기 쉽다.
- 인증, 스토리지, Edge Function을 나중에 붙일 수 있다.

단점:

- 외부 서비스 계정과 환경변수 관리가 필요하다.
- 완전 로컬 구조는 아니다.

### Neon PostgreSQL

Vercel과 조합이 좋고 서버리스 PostgreSQL로 쓰기 편하다.

장점:

- Vercel 배포와 궁합이 좋다.
- 브랜치 DB 같은 개발 편의 기능이 좋다.
- 순수 PostgreSQL에 가깝게 운영할 수 있다.

단점:

- Supabase보다 부가 기능은 적다.

### Railway PostgreSQL

이미 Railway를 사용 중이라면 괜찮은 선택이다.

장점:

- 앱과 DB를 한 프로젝트에서 보기 쉽다.
- 백엔드 서버를 따로 운영해야 할 때 편하다.

단점:

- 단순 Vercel 웹앱에는 Supabase/Neon이 더 가벼울 수 있다.

### SQLite

로컬 개인용으로는 좋지만 Vercel 배포 저장소로는 추천하지 않는다.

장점:

- 설정이 단순하다.
- 로컬 개발이 빠르다.

단점:

- Vercel 프로덕션에서 영구 저장소로 쓰기 어렵다.
- 여러 실행 환경에서 동시에 쓰기 곤란하다.

## 단계별 구현 방향

### 0단계: 정적 개인 허브

먼저 화면과 정보 구조를 만든다.

- 인수 준비 대시보드
- 테슬라 정보 보드
- 체크리스트
- 액세서리 비교표
- 수동 링크 저장
- 수동 메모

이 단계에서는 API 키와 비밀값을 쓰지 않는다.

### 1단계: Vercel + DB

정보 저장이 필요해지면 외부 DB를 붙인다.

- 저장한 글
- 태그
- 메모
- 체크리스트 완료 상태
- 액세서리 후보
- 구매 여부
- 중요도
- 검색어 묶음

추천 테이블:

- `sources`: 정보 출처
- `search_queries`: 검색어 묶음
- `search_results`: 검색 결과
- `saved_items`: 저장한 글
- `notes`: 개인 메모
- `tags`: 태그
- `checklist_items`: 체크리스트
- `decisions`: 구매/설치 의사결정

### 2단계: 네이버 공개 카페글 검색

네이버 공식 카페글 검색 API는 공개 카페글 검색 결과를 가져올 수 있다. 응답에는 제목, 링크, 요약, 카페명, 카페 URL 등이 포함된다.

주의할 점:

- 공식 카페글 검색 API는 비로그인 방식이다.
- 클라이언트 아이디와 시크릿은 서버에서만 사용해야 한다.
- 브라우저에 API 키를 노출하면 안 된다.
- 가입한 카페의 비공개 글 전체를 읽는 공식 범용 API는 확인되지 않았다.
- 네이버 로그인 API를 붙인다고 해서 모든 카페 글 읽기 권한이 생기는 것은 아니다.

따라서 첫 구현은 다음 방식이 적절하다.

- 내가 관심 있는 키워드를 등록한다.
- 서버에서 네이버 공개 카페글 검색 API를 호출한다.
- 결과를 DB에 저장한다.
- 화면에서 저장, 숨김, 태그, 메모를 할 수 있게 한다.
- 중요한 글은 사람이 직접 읽고 판단한다.

관련 문서:

- https://developers.naver.com/docs/serviceapi/search/cafearticle/cafearticle.md
- https://developers.naver.com/docs/login/cafe-api/cafe-api.md
- https://developers.naver.com/docs/login/api/api.md

### 3단계: TeslaMate 연동 검토

차량 인수 후 실제 주행과 충전 데이터가 쌓이기 시작하면 TeslaMate를 별도 서비스로 운영할지 판단한다.

TeslaMate는 이 레포의 Next.js 앱 안에 넣는 기능이 아니라 별도 Docker 서비스로 보는 것이 맞다. 나중에 우리 앱은 TeslaMate의 PostgreSQL DB에서 필요한 요약만 읽거나, 수동으로 내보낸 데이터를 가져오는 식으로 연결한다.

자세한 내용은 [TeslaMate 설명](teslamate.md)을 본다.

## UI 방향

흔한 관리자 대시보드처럼 보이면 안 된다. 테슬라 오너가 실제로 자주 확인하는 개인 관제판처럼 만든다.

원칙:

- 첫 화면은 홍보 페이지가 아니라 실제 앱 화면이어야 한다.
- 정보는 카드보다 표와 리스트 중심으로 빠르게 훑을 수 있어야 한다.
- “신호”, “할 일”, “결정”을 분리한다.
- 색상은 과하게 어둡거나 보라색 위주로 가지 않는다.
- 실제 차량, 충전, 지도, 문서 같은 현실 정보가 중심이 되어야 한다.
- 버튼과 메뉴 문구는 전부 한글로 쓴다.
- 전문 용어는 짧은 설명을 붙인다.

## 결론

지금 만들 것은 TeslaMate 대체제가 아니다.

지금 만들 것은 다음에 가깝다.

- 테슬라 인수 준비 앱
- 테슬라 정보 큐레이션 앱
- 개인 의사결정 기록 앱
- 추후 차량 데이터 대시보드로 확장 가능한 기반

기술 선택은 Vercel + Next.js + Supabase 또는 Neon PostgreSQL 조합을 1순위로 둔다.

다음 작업은 한글 UI 기준으로 Next.js 앱을 초기화하고, 목데이터 기반의 첫 화면을 만드는 것이다.
